# Security

This document describes what the code does and how each claim was checked. "Checked" means a test or command ran and passed in this repository's environment. "Not verified" means it was not, and why. No part of this application has had an independent security review or a penetration test.

## System and data flows

```
(1) Browser ──HTTPS, session cookie──▶ Buildr server
(2) Buildr server ──user JWT, RLS──▶ Supabase Postgres   projects, files, messages
(3) Buildr server ──service role, named functions──▶ Supabase   credits, audit, assistant messages, export, delete
(4) Buildr server ──API key──▶ OpenRouter ──▶ model provider   prompt, project files, tool results
(5) Buildr server ──5-char SHA-1 prefix──▶ Have I Been Pwned   password breach check
(6) Buildr server ──REST──▶ Upstash Redis (optional)   hashed rate-limit keys
```

| Flow | Data                                                                                                       | Notes                                                                                                                                                |
| ---- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Credentials at sign-in, chat text, files                                                                   | Cookies are `httpOnly`, `sameSite=lax`, `secure` in production.                                                                                      |
| 2    | Everything the person owns                                                                                 | Row Level Security is the enforcement point; server code checks ownership too.                                                                       |
| 3    | User id, amounts, event names, assistant messages                                                          | Only `lib/db/service.ts` holds the service key and it exports named operations, not a client. ESLint forbids importing it from components and pages. |
| 4    | The person's message, recent history, the file list, file contents (up to 60 KB per request), tool results | This is the main privacy exposure: project content leaves the system. See subprocessors.                                                             |
| 5    | Only the first 5 hex characters of the password's SHA-1                                                    | k-anonymity range query. If the service is unreachable the check is skipped and a warning logged (fails open).                                       |
| 6    | SHA-256 hashes of user ids, IPs, emails, with counters                                                     | No raw IPs or emails in Redis or logs.                                                                                                               |

## Trust assumptions

- **Client IP headers.** Per-IP limits read `x-real-ip` or the first `x-forwarded-for` value. These are trustworthy only behind a proxy that sets them and strips client-supplied copies (Vercel does). If the app is exposed directly, an attacker can rotate fake IPs and bypass IP limits; per-account limits still apply. With no header at all, all callers share one bucket (KI-8).
- **Single instance limits.** Without Upstash, rate limits and the one-response-at-a-time lease are per process (KI-6, KI-18).
- **Supabase is configured as documented.** Email confirmation on, redirect URLs restricted, and the migration applied as written.
- **The model is not trusted.** Nothing relies on it obeying instructions; see the threat table.

## Other controls

- **Supply chain.** Exact version pins (enforced by a test), `npm audit` in CI and in `ship-check`, Dependabot configuration, CodeQL workflow, gitleaks in CI and pre-commit. The workflows have not run (KI-2).
- **Terms and privacy.** Placeholder pages exist and say plainly that they have not been reviewed by a lawyer.
- **Data subject requests.** Export and deletion are implemented (Account page, `/api/account/export`, `/api/account/delete`) and unit tested with mocked storage; the underlying `export_user_data` function and deletion cascade are integration tested.
- **Live preview sandbox.** Generated code runs in an iframe sandboxed without `allow-same-origin`, so it has an opaque origin: no cookies, no storage, no DOM access to the app and no credentialed requests. Its policy allows network only to esm.sh, and the frame document accepts messages only from the embedding window at the deployment's own origin. The transpiler runs in the app page but never evaluates code (sucrase and es-module-lexer are parsers), so the app's strict CSP is unchanged. Residual risks: the preview trusts esm.sh and cdn.tailwindcss.com as supply chain for the sandbox only (not the app), and generated code can make GET requests to esm.sh, which is not a data channel of concern. `allow-forms` and `allow-modals` are granted so generated apps behave; `allow-popups` and `allow-top-navigation` are not.
- **Pending prompt in the browser.** The home-page prompt is kept in `localStorage` until the person has signed in. It is untrusted on the way back: it is length-capped on save and on read, dropped if malformed or older than a day, sent only into the project whose id was recorded with it, and validated by the chat route like any typed message. Client components import limits from `lib/security/limits.ts`, not from the Zod schemas, because Zod 4 compiles parsers with `new Function` and the CSP forbids `eval` (a guardrail test enforces this).
- **Not implemented:** MFA enrolment, an admin console, automatic retention limits on chat messages, per-request zero-data-retention routing, and an alert when spend crosses a threshold.
